# User-document conformance ledger

This ledger compares the VitePress user documentation in `website/` with executable behavior.
The user documentation is authoritative. A row is complete only when its public schema, compiler,
adapter, and relevant HTTP response are backed by regression evidence.

## Closed in the current conformance loop

| Contract | Implementation evidence |
| --- | --- |
| Atomic limits apply per statement and cumulatively | Worker rejects cumulative rows, bytes, and elapsed time before commit and suppresses partial results |
| Conditional output distinguishes denied NULL from visible database NULL | Compiler-owned visibility companions are emitted, validated, stripped, and reported as cell redactions |
| SQL coverage is based on execution, not fixture declarations alone | Coverage checker requires digest-bound `executed-fixtures.json`; twenty-two fixture pairs execute before evidence is written |
| Execute requires concrete parameter values and types | Verified compilation rejects missing, extra, and mismatched client parameters |
| Explain may omit parameter values when use proves the type | Bound-expression traversal supplies typed placeholders only for Explain |
| Catalog JSON Schema accepts the documented Draft 2020-12 safe subset | Activation accepts the closed finite subset and rejects remote `$ref` |
| `IN`, `NOT IN`, `IS NULL`, and `IS NOT NULL` | Binder, policy compiler, AST emission/reparse, structural invariant check, negative control, and reference SQLite differential fixture pass |
| Mutation metadata reports operation-check state | Sealed plan exports only whether an operation check existed; Worker returns `passed` or `not_configured` after successful validation |
| Public SQL errors use the documented stable taxonomy | Parser, policy, parameter, limit, snapshot, authentication, and result-contract failures are normalized without resource or column detail; denied E2E cases prove zero database egress |
| Statement failures expose a safe RFC 6901 path | Gateway preserves the failing index and HTTP returns `/statements/N`; no resource, column, predicate, or parameter value is included |
| Explain publishes safe resource usage | Internal numeric IDs remain in the private compile/cost ABI; HTTP resolves role-visible Catalog names and client-referenced columns from bound provenance |
| JSON object/array parameters require a Catalog-proven JSON use | Binder-derived expected types are consulted before conversion; JSON values become lossless internal text only for `json` parameters and are rejected for scalar uses |
| Explain parameter descriptors come from compilation | Private ABI carries the verified logical parameter type, so missing-value placeholders are never reinterpreted as another type by JavaScript |
| Catalog build and value contracts | Deployment Catalog build captures `PRAGMA table_xinfo`, activation checks physical mappings and derives omitted basic types, compiled descriptors retain storage/format/constraints/JSON Schema, and both client parameters and remote results are revalidated |
| JSON path result typing | Execute uses the supplied SQLite JSON path to narrow the retained JSON Schema; missing-path Explain emits a stable finite logical-type union and remote rows are validated against that union |
| JSON table and collection queries | The closed SQLite-compatible `json_each`/`json_tree` plus `json_group_array(value)` shape retains root-column provenance, composes the row policy in the same SQL, returns exactly one JSON-array row with element Schema, and is covered by sealed SQL and reference-SQLite differential execution |
| Typed projection expressions and function registry | Searched `CASE`, string `||`, and `CAST(... AS TEXT)` have closed typed IR nodes; every input/branch is permission checked, converted to a SQLite AST, emitted by the parser library, structurally reparsed, and differentially executed, while the deployed function registry matches Capabilities (`count`, `lower`, `upper`, `json_extract`, `row_number`) |
| Subqueries and CTEs | Capabilities now names the accepted closed forms: qualified correlated `EXISTS`, transparent derived source, and one transparent/filtered nonrecursive CTE feeding an optional outer JOIN; each form has provenance, shadowing, row-policy, sealed-SQL, and reference-SQLite evidence |
| Cloudflare commit checks | Activated check metadata is exported only to the trusted adapter; Atomic Execute and interactive commit run sorted triggered checks in the owning Durable Object, sign HTTPS hooks, expose hashed short-lived SELECT-only capabilities, compile callback SQL through the gateway on the same Turso transaction, and roll back on deny, timeout, protocol/sequence error, callback failure, or owner loss. The dev release smoke (`provision-dev.mjs`, #42) drives the development-only `smoke_check` through a separately deployed validator Worker (`deploy/cloudflare/dev-validator/`) on the deployed Worker, Durable Object and Turso: Atomic Execute allow and deny, interactive commit allow, and an interactive commit whose validator answers after the hook deadline (409 `POLICYSQL_COMMIT_CHECK_REJECTED`). Every allow requires the validator's signed-hook verification and its callback SELECT to see the uncommitted probe row; a final read proves the denied and timed-out commits left no row. Owner loss is not exercised in the real environment (no supported way to evict one Durable Object on demand; a redeploy restart lands after the four-second transaction deadline) and stays covered by the local owner and step-machine tests |
| Constant `SELECT` | Resource-free numeric literal projections compile as a distinct default-safe IR, are AST-emitted/reparsed/verified, expose no fake resource or policy, and report `integer`/`number` descriptors |
| Generated TypeScript and Kysely boundary | `policysql generate` uses Catalog/Capabilities/Explain, pins snapshots and hashes, atomically replaces artifacts, and the client/Kysely packages route named SQL only through the gateway without database credentials |
| Development deployment SQL surface | The deployed Catalog and physical Turso schema contain the documented author/post/comment/archive resources; compile regression covers every advertised SQL family and the release gate executes fourteen read statements plus a seven-statement mutation/expectation rollback batch, then proves the probe row is absent. The smoke starts only after five consecutive rounds in which the Worker, a fresh Durable Object and the validator report the version ids `wrangler deploy` printed (reference-wrapper `policysql-deployment-version` header and `/healthz/owner`, from Cloudflare's version metadata binding; the library reads no platform binding), and every smoke response must carry the new version |
| Deployment-independent bytes contract (#17, ADR 0016) | Shared canonical base64 vectors, Rust input/result/preset tests, platform-independent Client/Kysely/generator tests, and real-WASM/JWT/Turso-HTTP/file-SQLite tests cover client and preset BLOB binding, physical type/hash equality, nullable-result NULL and empty bytes, NULL bytes parameters only in proven nullable assignments (ADR 0017), policy denial/redaction, malformed input, size limits, callback/interactive execution, rollback and replay. |
| NULL named parameters in nullable assignments (#20, ADR 0017) | Native tests prove acceptance equals the statement-wide proof for every logical type, cover shared parameters, forbidden/preset/tenant columns, and evaluate post-state checks on the NULL-assigned row in an independent SQLite database (UNKNOWN fails like FALSE). The `tests/fixtures/nullable` cases run at the WASM ABI and through real WASM/JWT/Turso-HTTP/file-SQLite, covering Explain `nullable`, physical SQL NULL, rollback on check/NOT NULL/trigger/later failures, idempotent replay and interactive transactions. |
| Bytes and NULL assignment real-deployment conformance (#42) | The dev release smoke runs on the deployed Worker and Turso against the development-only `smoke_values` resource (nullable text `note`, nullable bytes `payload`, non-nullable `label`): padded 4-byte, empty and 3,001-byte BLOB round trips through `RETURNING` and `SELECT` return the exact canonical base64; a read value is accepted unchanged as a parameter; `maxBytesPerValue + 1` decoded bytes is 413 `POLICYSQL_LIMIT_EXCEEDED` and writes nothing; unpadded input is 400. JSON `null` stores SQL NULL in both nullable columns (proved by `IS NULL`), `null` for `label` or in a comparison is 400 `POLICYSQL_INVALID_PARAMETER`, and Explain reports `nullable` true only for `note` and `payload`. |
| Client SQL string literals bind their decoded value (#39) | The binder strictly decodes `'...'` tokens (`''` escape only) and rejects double-quoted, unterminated and blob literals; the emitted-plan verifier re-encodes client literal values against their original tokens and rejects any unexplained quoted server literal. Native golden/differential tests cover `=`, `!=`, `<>`, `<`, `>`, `LIKE`, `GLOB`, `IN`, `CASE`, `||`, `CAST`, INSERT VALUES, UPDATE SET and DELETE against unprotected single-tenant SQLite, plus other-tenant isolation and a policy `neq` check on a written literal. The `sqlite.security.string-literal-decoding` fixture and the real-WASM/JWT/Turso-HTTP/file-SQLite harness cover `= 'seed'`, `LIKE 'se%'` and `UPDATE ... WHERE id = 'seed'`. A NUL inside a literal is rejected as SQLite does; other control characters match SQLite. The dev release smoke (`provision-dev.mjs`) permanently requires `WHERE id = 'project_a'` and `WHERE name LIKE 'Alph%'` to return the seeded row on the deployed Worker and Turso. |
| Turso/Hrana bytes response normalization | HTTP transport fixtures cover padded and unpadded database BLOB responses, malformed encodings and decoded size boundaries. The SQLite-backed HTTP harness emits unpadded BLOBs; SELECT results can be submitted unchanged as bytes parameters, while unpadded public inputs are still rejected. On the real deployment the dev release smoke records Turso's Hrana pipeline returning an unpadded BLOB (`X'000102FF'` as `AAEC/w`) and requires the deployed Worker to return the canonical padded `AAEC/w==`. |

## Remaining externally visible differences

| Contract | Outstanding implementation and evidence |
| --- | --- |
| Durable Object owner loss in the real environment | Owner loss is verified only locally (owner port, switch and step-machine tests). The real-environment smoke cannot evict one object on demand, and a redeploy restart lands after the four-second transaction deadline, so it would observe expiry rather than loss (#42). |

Future backend profiles and newly advertised SQL leaves require their own conformance rows and
evidence before release. Defining a shared Client contract does not establish support for another
backend profile.

## Audit rule

Do not remove a difference by weakening the user documentation unless a new accepted specification
decision explicitly changes the contract. For each row, add the user-document clarification first,
then regression and bypass tests, then implementation, then rerun workspace Clippy/tests, execution
coverage, schema validation, Worker tests, and the documentation build.
