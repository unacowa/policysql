PolicySQL / Developer Architecture

SQLを信頼せず、意味を証明してから実行する。

PolicySQLは、信頼できないSQLをCatalogへバインドし、宣言的ポリシーを組み込んだ保護済みSQLへ変換する default-denyのポリシーコンパイラです。初期profileはSQLite/Turso、将来のDB対応はdialect一式をversioned Backend Profileとして追加します。

01 / System boundary

全体構成と信頼境界

PolicySQLプロセスがセキュリティ境界です。SQL、パラメータ、HTTP入力、外部検証応答、DBエラーはすべて未信頼として扱い、 検証済みのポリシー、論理Catalog、認証済みセッションだけをコンパイル入力として信頼します。

◆

重要: PolicySQLの中心成果物はHTTPサーバーやSQLパーサ単体ではなく、入力SQLの意味を解決し、ポリシーを保持したSQLを生成・再検証するコンパイラです。

02 / Components

コンポーネント責務

各レイヤーは、前段を暗黙に信頼しません。構文解析、名前解決、ポリシー適用、SQL生成、再検証を分離し、曖昧さがあれば閉じて拒否します。

Gateway

Workerへ実装済み

JWTとaccess scopeを検証し、trusted sessionを構築。request envelope、version precondition、resource limitを検査し、compiler・adapter・監査を統合します。

Dialect Frontend

SQLiteを検証済み

profileがadvertiseするSQL dialectで、itemごとに厳密に1 statementを解析します。parser固有ASTは外へ漏らさず、project-owned bound IRへ変換します。

Binder / Catalog Resolver

Rustで実装済み

table、alias、CTE、columnを安定したResourceId / ColumnIdへ解決し、曖昧な参照を拒否。式・出力・相関参照のprovenanceと論理型を追跡します。

Policy Kernel

Rustで実装済み

resource × role × operationでpolicyを選択。row filter、column permission、limit、preset、operation check、commit check計画をbound IRへ適用します。

Backend Emitter

SQLite実装済み

protected relational planをprofile固有のtyped ASTへ変換し、server-owned parameterを割り当て、parser libraryのtoken emitterだけでSQL化します。PostgreSQLを含む別dialectは独立emitterとして追加します。

Invariant Verifier

SQLite実装済み

同じpublic dialectで出力SQLを再parseし、protected statementとAST構造を比較します。さらにoperation、parameter ownership、result、snapshot、mutation invariantを照合し、文字列整形の一致には依存しません。

Database Executor

実Tursoへ常設

matching profileが生成したexecution handleとprotected SQLだけをatomic batchへ送り、raw resultをRustで再検証します。任意のSQL文字列や別profileのplanは実行できません。

Transaction Owner

DOで検証済み

1つのopen Turso transactionを所有し、client操作、commit / rollbackを直列化。auth/session fingerprint、sequence、exact retry、4秒期限を固定し、ownerやconnectionの喪失をterminal failureとして扱います。外部commit checkは未advertiseです。

03 / Multi-database boundary

04 / Compile pipeline

1 statementのコンパイル経路

実行前に、すべてのstatementをコンパイル・認可します。構文ASTだけでpolicyを適用せず、Catalogへ解決したbound representationを必ず経由します。

入力を正規化する

endpoint access、JWT、role、session、request size、statement数、named parameterを検証。client parameterとserver namespaceを分離します。

不変snapshotを固定する

1 request / transactionでpolicy、Catalog、registry、compiler、Backend Profileの同一versionをpinします。古いexpected versionはDBを開く前に失敗します。

Parseしてsubsetを絞る

各sql fieldを厳密に1 statementとしてparse。DDL、transaction control、PRAGMA、ATTACH、unknown functionなど、advertiseしていない構文はdefault-denyで拒否します。

CatalogへBindする

すべてのtable / alias / column / CTEを安定IDへ解決。usage contextとprovenanceを追跡し、unknown・ambiguous・unprovableな参照を拒否します。

Policyを合成する

operation・resource・roleに対応するpolicyを選択し、client predicateを置換せずANDでrow filterを合成。column permission、limit、preset、RETURNINGも独立に検査します。

Protected planからSQLをEmitする

選択済みprofileがserver-owned parameterを割り当て、dialect固有SQL、result descriptor、operation-check計画、explain traceを生成します。

再Parseして不変条件を検証する

生成物を独立にparse / bindし直し、policy coverage、resource / column access、statement count、join placement、parameter ownershipを照合。合格したSQLだけを実行層へ渡します。

SELECT row policyの合成例（SQLite profile）

caller条件は保持し、policy条件を同一statementへ組み込みます。policy limitはcaller limitとの小さい方です。

SELECT id, title
FROM posts
WHERE (status = :status)
  AND (tenant_id = :__policysql_session_tenant_id)
LIMIT 100

LEFT JOINのpolicy配置

nullable側のfilterをWHEREへ置くとouter joinが壊れます。右側resourceのpolicyは、そのnull-extension境界のON predicateへ配置します。

posts policy
WHERE
＋
authors policy
JOIN ... ON

05 / Execution envelope

Atomic実行とcommit check

stateless実行は POST /v1/transactions:execute の1 endpointへ統一します。ordered array内の全itemを先にcompileし、 全件SELECTならread、1件でもmutationならwriteとしてmodeを推論します。

Atomic Execute

全statementsをcompile / authorize
mode、idempotency、累積limitを検査
1 transactionで配列順に実行
operation checks → commit checks
全成功ならcommit、失敗なら全rollback

partial resultは返しません。responseのresults[]は0-based indexでrequestと対応します。writeにはIdempotency-Keyが必須です。

External Commit Check

Transaction ownerがvalidating phaseへ遷移
短命・read-only callback capabilityを発行
validatorのSELECTも通常のcompilerを通す
allow → commit / deny・timeout・owner loss → rollback

validatorはroleを選べず、mutation、commit、rollback、DB credential取得もできません。明示roleはclient入力ではなくimmutable policyが与えるsystem privilegeです。

06 / Mandatory invariants

実装が守る主要不変条件

この一覧は開発時の最小チェックリストです。新しいSQL surfaceを増やすたびに、positive / negative / bypass / differential testを追加します。

Default deny未知のstatement、node、clause、function、metadataは拒否。
Exactly one statement1 sql fieldにつき厳密に1 statement。semicolon smugglingを許可しない。
Bound authorizationtext matchではなく、解決済みResourceId / ColumnIdへpolicyを適用。
Complete coverageすべてのbase-table accessにoperation policyが必要。missing policyはdeny。
Column non-interference禁止columnはprojection以外のfilter、join、sort、aggregate等でも使用不可。
Server namespace integrityclientはsession parameterやpreset columnを定義・上書きできない。
Atomic checksmutationとpost-state checkは同じtransaction内。check-then-query認可は禁止。
Emission verification出力SQLを再parseし、別checkerで実行前に不変条件を再確認。
Bounded resources時間、行、bytes、depth、joins、params、complexity、statement数を制限。
Unique result identity出力名は非空で、profileが定める識別規則のもとで一意。
Snapshot integritytransaction中のpolicy / Catalog / registry / backend profileを不変に固定。
Safe errorshidden schema、policy、credential、protected SQL、raw DB errorを漏らさない。

08 / Current state

現在地と実装順序

SQLite/Turso v1 compiler、JWT、Capabilities、Catalog、Explain、単一table SELECT、bounded mutation、response後のcost observation、persistent idempotency、Durable Object interactive transactionをCloudflare Workerと実Tursoへ常設しました。外部commit checkと未対応SQLはCapabilitiesでadvertiseせず拒否します。

仕様として確定

  • default-deny / single statement
  • policy semanticsとtrusted session
  • atomic envelope / commit-check protocol
  • Catalog・result descriptor contract
  • versioned Backend Profile境界

常設環境で運用検証

  • 実Tursoのexact rows read / written
  • mutation post-state checkとrollback
  • persistent idempotency replay / conflict
  • DO transaction owner / expiry / owner loss

常設Workerでadvertise

  • single-table parameterized SELECT
  • explicit projected columns
  • simple boolean predicate + row filter
  • policy limit、emission、re-parse、explain
  • JWT / rate limit / Turso result再検証
  • response後のEXPLAIN QUERY PLAN cost観測（planner proseは非authoritative）
  • INSERT / UPDATE / DELETE
  • interactive transaction / exact retry
→

拡張原則: 初期実装はSQLite/Turso profileへ集中します。PostgreSQLはfrontend、Catalog、emitter、独立verifier、codec、executor、conformance testが揃うまでadvertiseしません。
