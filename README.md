# PolicySQL

PolicySQL is an experimental open-source SQL policy gateway.

It accepts **untrusted, parameterized SQLite SQL**, parses and binds it against a known schema, applies declarative row/column/mutation policies, coordinates optional external commit checks, and emits **protected SQLite SQL** for execution against Turso Database.

> Status: the SQLite/Turso v1 compiler profile and its security test contract are implemented; deployment-specific network transports still require conformance testing. Not production ready.

## Core idea

```text
Application / AI-generated code
        |
        | SQLite SQL + named parameters
        v
PolicySQL Gateway
  1. Accept one or more ordered SQL items
  2. Parse exactly one SQL statement per item
  3. Bind tables, aliases, columns, and expressions
  4. Reject unsupported or unsafe syntax
  5. Compile declarative policies into each query
  6. Apply server-owned presets
  7. Re-parse and verify protected SQL
  8. Execute all items atomically and run checks
        |
        v
Turso / libSQL
```

PolicySQL is not intended to be a generic SQL proxy in its first releases. It starts with a strict, default-deny SQL subset and expands only when policy-preserving transformations are proven and tested.

## Goals

- Use SQL as the public query and mutation language.
- Preserve Hasura v2-style declarative authorization semantics without requiring GraphQL.
- Enforce row and column permissions by rewriting the query itself.
- Support session-derived values such as `tenant_id`, `user_id`, and `role`.
- Support insert/update presets, pre-operation filters, post-operation checks, and external transaction commit checks.
- Target SQLite-compatible SQL and Turso Database MVCC first.
- Provide explainability: show accessed resources, applied policies, rejected features, and protected SQL.
- Be suitable for code generated by humans or AI, while treating every incoming SQL statement as untrusted.

## Non-goals for the initial implementation

- Full SQLite grammar support.
- PostgreSQL wire-protocol compatibility.
- PostgreSQL-to-SQLite transpilation.
- DDL or migration execution through the public SQL endpoint.
- Stored procedures, triggers, `ATTACH`, `PRAGMA`, extension loading, or arbitrary functions.
- Transparent compatibility with every ORM.
- Treating generated SDK types as a security boundary.

## Start here

1. Read [`docs/codex-handoff.md`](docs/codex-handoff.md).
2. Read [`docs/security-model.md`](docs/security-model.md) before implementing rewrites.
3. Keep the initial SQL subset intentionally small.
4. Add a failing security regression test before broadening parser/compiler behavior.
